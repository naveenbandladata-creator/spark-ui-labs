**Q1.** `Scan parquet`: **number of partitions read = 12**, files read = 24. A March report needs **1** partition.

**Q2.** `sales.filter(month_name("month") == "Mar")`. The filter goes through a Python UDF, and Spark can't see
inside a UDF, so it can't work out which folders to skip. You can spot the UDF in the graph as **BatchEvalPython**,
and the Filter after it is the one that drops 2,400,000 rows to 200,000: Spark read everything first, then threw 92% away.
Fix: filter on the column itself, `F.col("month") == 3`.

**Q3.** **BroadcastHashJoin: 200,000 rows in from sales, 800,000 out.** Every sale matched 4 lookup rows, because the
lookup table holds each store 4 times (BroadcastExchange shows 1,200 rows for 300 stores).
This is not just slow, it's **wrong**: every revenue number in the report is 4x too big.
The row counts in the SQL tab are often the fastest way to catch a bad join.

**Q4.** BroadcastHashJoin, a good choice: the lookup is tiny, so copying it to every executor avoids shuffling 2.4 million rows.
The join type was fine; the duplicate rows were the problem.

**Q5.**
```python
clean_lookup = lookup.dropDuplicates(["store_id"]).select("store_id", "region")
(sales.filter(F.col("month") == 3)                 # partition pruning: 1 folder read
      .join(clean_lookup, "store_id")              # 200,000 in, 200,000 out
      .groupBy("region").agg(F.sum("amount").alias("revenue"), F.count("*").alias("rows"))
      .orderBy("region").show())
```
