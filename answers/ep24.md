# Ep 24 - Final exam: answers
(From the reference run. Your numbers will be close, not identical.)

## Job 1: nightly export -> spill from too few partitions
- **Screen:** Stages tab, the sort stage (2 tasks). **Spill (Disk) ~270 MB**, Spill (Memory) ~336 MB; each task ~11 s.
- **Why:** 5 million rows sorted in only 2 partitions, so each task holds half the data in a 512 MB executor.
- **Fix:** more shuffle partitions (or turn AQE on and let it size them), so each task's slice fits in memory.

## Job 2: dashboard tiles -> the same expensive work done three times
- **Screen:** Jobs tab. Three "dashboard tile" jobs, **each with the same 4 stages** (read, distinct, aggregate...).
  The SQL tab shows the same graph three times, each starting from Range.
- **Why:** `events` is recomputed for every action. Nothing is cached.
- **Fix:** `events.cache()` (then one action to fill it), or compute all three tiles in one `agg(F.sum(..), F.max(..), F.avg(..))`.

## Job 3: weekly KPI -> work moved to the driver
- **Screen:** Jobs tab, Event Timeline. A **~5 s gap** before "save weekly KPI" with no job running: the executors are idle.
- **Why:** `toPandas()` pulls 400,000 rows to the driver, then pandas computes a median there, alone.
- **Fix:** let Spark do it: `groupBy("weekday").agg(F.median("value"))` (Spark 3.4+), and only bring back 7 rows.

# The 5-minute Spark UI checklist
1. **Jobs tab.** How many jobs? More than you expected = repeated work or debugging actions left in. Any gaps in the
   Event Timeline = the driver is working alone (collect, toPandas, Python loops).
2. **Find the slowest stage** (Stages tab, sort by Duration). Everything below is about that stage.
3. **Summary Metrics: Max vs Median.** Duration and Shuffle Read Size. Max far above median = skew.
   Check **bytes**, not only records: pre-aggregation can hide skew in record counts.
4. **Spill (Memory / Disk)** columns. Spill = partitions too big for executor memory: more partitions or less data per row.
5. **Task count vs cores.** Thousands of tasks lasting milliseconds = too many partitions. Fewer tasks than cores = too few.
6. **Executors tab.** Dead executors, failed tasks, high GC time. Exit code 52 = out of memory.
7. **SQL / DataFrame tab, top to bottom.** Scan box: partitions and files read (did it skip data?).
   Row counts on every box (does a join multiply rows?). Join type (Broadcast vs SortMerge). Exchange boxes = shuffles.
   BatchEvalPython / ArrowEvalPython = Python UDFs.
8. **Storage tab.** Is the cache you expect there, and at 100%?
9. **Environment tab.** Confirm the settings the job really ran with.
