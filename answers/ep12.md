# Ep 12 - Spot the Problem #2: answers
(Your numbers will differ a little. These come from the reference run.)

**Q1.** The second stage (8 tasks, with Shuffle Read). The slowest task took about 2.2 s against a median of about 0.23 s: roughly 10x.

**Q2.** Shuffle Read Size / Records:
- Records: median 124, max 146. Looks fine.
- Size: median about 1.9 MB, max about 48 MB. About 26x. **The size is the truth.**

**Q3.** `collect_list` is combined on each machine before the shuffle. The 750,000 "guest" orders are split over 2 machines, and each machine
sends its ~375,000 as **one record**: a single huge list. So the record count stays small while the bytes explode.
Lesson: when you hunt for skew, check bytes and task duration, not only record counts.

**Q4.** Any two of:
- Don't collect what you don't need: if you only need the count, drop `collect_list` (the 48 MB vanishes).
- Handle the hot key separately: filter out `"guest"` (often it's a placeholder, not a real customer), summarize it on its own, then union.
- Salt the hot key: add a random 0-9 suffix to `"guest"`, aggregate, then combine the ten partial results.
- Turn AQE back on with skew handling. It helps most with skewed **joins** (Ep 19 shows what it can and can't fix).
